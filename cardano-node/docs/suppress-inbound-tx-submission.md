# Suppressing incoming transaction diffusion

This experimental node option suppresses node-to-node TxSubmission2 traffic from peers into this node's mempool. It leaves local socket submission, outgoing transaction serving, chain-sync, block-fetch, and Leios protocols enabled. Default behavior is unchanged.

```sh
cardano-node run --config config.json --topology topology.json \
  --database-path scratch-db --socket-path scratch.socket --port 3011 \
  --suppress-inbound-tx-submission
```

Alternatively, put `"SuppressInboundTxSubmission": true` at the root of the selected JSON/YAML configuration file. For a cardano-config envelope, this is a root sibling of `Configuration`; it is a fork extension, not an upstream cardano-config field. The setting is read from the selected file, not from inherited envelope files. Omission means false; null, strings, and numbers are rejected. The CLI overrides the file: `--no-suppress-inbound-tx-submission` explicitly restores normal behavior. The option is startup-only; restart the standalone node to change it. SIGHUP does not change the active diffusion applications.

The relevant direction is the **TxSubmission2 responder**, despite its server name: it requests identifiers and bodies from peers and writes accepted transactions to the mempool. The initiator reads our mempool and serves transactions outward. The adapter in [TxSubmissionPolicy.hs](../src/Cardano/Node/TxSubmissionPolicy.hs) uses the existing `stdLowLevelRunNodeArgsIO`/`runWith` extension point and changes only `daApplicationInitiatorResponderMode`. Across negotiated protocol versions and protocol temperatures, it replaces only the responder callback for the exported `txSubmissionMiniProtocolNum` (wire number 4). The initiator callback, mini-protocol registration, start strategy, ingress limits, local responder application, and other applications are retained.

The replacement waits on a cancellable timer without reading the channel, sending a request, or invoking the inbound mempool handler. It does not return immediately, because normal mini-protocol termination can close the whole multiplexed connection. A compliant TxSubmission2 peer waits for requests, so this node never asks it for transaction identifiers or bodies. Mux can still receive the peer's initial protocol message; this is not a packet firewall. Misbehaving peers remain subject to mux ingress limits. Transactions in fetched blocks or Leios endorser blocks are outside this policy; this option is not a ban on receiving transaction data through consensus synchronization.

The disabled path calls the stock `Node.run` directly. Both TxSubmission logic versions are covered because the enabled path bypasses their common responder application before either inbound handler starts. Local transaction admission and actual outward delivery still depend on validity, mempool capacity, and having a peer that requests the transactions.

The source baseline is node `65dd69d103e41a749d428ffd05de153ef7c2ab45` (rc-2026w43), with consensus `a337d69f4946d5a1b20ecaaeae635dd47822e3d2` and network `f0243fe6d962e922ab2c8e131543eba3d78748cb` pinned in [cabal.project](../../cabal.project). This release keeps the existing network but requires a fresh database sync. Use a separate process, port, socket, and scratch database for qualification; do not reuse a running node's database.

The policy suite uses both existing configuration dialect fixtures, the real CLI parser and startup configuration resolver, ON/OFF precedence and invalid-value checks, negotiated versions, and callback execution. It repeats the sequence in one process and verifies that the blocked responder is cancellable without invoking its original handler or channel. These are configuration and wiring tests, not a substitute for a standalone node diffusion smoke test.

For the bounded three-node devnet, supply the candidate, an existing w42 instrumented binary for parity, and the w43-compatible CLI. This creates fresh keys and disposable balances on magic 1414, connects only over loopback, submits two transactions there, and stops every process it starts. It never uses a live-network socket or treasury. The directory must not already exist.

```sh
python3 cardano-node/test/tx-submission-policy/smoke.py \
  --node /path/to/candidate/bin/cardano-node \
  --baseline /path/to/w42/bin/cardano-node \
  --cli /path/to/compatible/bin/cardano-cli \
  --config-template cardano-node/test/cardano-config-compare/config/config.json \
  --root /path/to/new-devnet-directory
```

The runner first checks block synchronization with suppression enabled, then pauses forging while checking peer exclusion and local outward diffusion. It restarts the target without the flag to check stock admission, resumes forging to check inclusion, and compares schema-2 identity payloads for the same transaction against w42. It records every query outcome; an unsuccessful or unknown mempool query is an error, never evidence of absence. The genesis security parameter leaves enough ledger forecast horizon for the deliberate pause. Receipts and generated data stay outside the source tree.

The separate [passive sync runner](../test/tx-submission-policy/passive-sync.py) verifies the magic-164 October 18 Shelley genesis SHA-256 before connecting to an existing loopback relay. It starts a candidate with suppression enabled on a distinct port and scratch database, reads at least five historical blocks, then shuts down. It submits no transactions. This checks startup/sync, not catch-up to the current network tip. Run it only where such a passive check is authorized:

```sh
python3 cardano-node/test/tx-submission-policy/passive-sync.py \
  --node /path/to/candidate/bin/cardano-node \
  --cli /path/to/compatible/bin/cardano-cli \
  --config /path/to/running-relay/network/config.json \
  --root /path/to/new-passive-directory --peer-port 3010 --port 34611
```

Neither smoke is a load test or evidence for unattended resource sizing. Full fleet rollout, database replacement, and network migration are outside these runners.
